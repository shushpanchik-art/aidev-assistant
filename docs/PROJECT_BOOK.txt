================================================================================
1. ЧТО ЭТО ЗА ПРОЕКТ И ЗАЧЕМ
================================================================================
AIDEV Assistant — это приватный веб-агент, который помогает вести разработку
других проектов (в первую очередь двух Telegram-ботов: SMOKI и smoktolk).

Владелец через браузер (доступ по SSH-туннелю) ставит задачу ТЕКСТОМ. Дальше:
  - агент читает нужный код в изолированной ПЕСОЧНИЦЕ (без секретов);
  - генерирует правки/новые файлы с помощью нейросети Google Gemini;
  - САМ прогоняет проверки (синтаксис, ruff, mypy, bandit, pytest, smoke) — GATE;
  - если проверки красные — сам чинит (несколько итераций);
  - старшая модель (PRO) выносит ВЕРДИКТ вместо владельца (ревью);
  - показывает человеко-читаемое описание изменений и рисков;
  - по кнопке оформляет Pull Request на GitHub.

ГЛАВНЫЙ ПРИНЦИП: в прод НИЧЕГО не уходит без ручного мержа PR владельцем.
Владелец смотрит PR на GitHub и мержит руками — это единственная точка входа
в прод. Агент никогда не получает bash/rm/curl и не пишет в рабочие каталоги.

ЦЕЛЬ ВЛАДЕЛЬЦА: исключить себя как звено между ИИ и терминалом. Владелец
ставит задачу текстом (+ может докинуть файлы/скриншоты), агент сам находит
файлы, правит, гоняет gate, чинит; PRO ревьюит; владелец только мержит.

================================================================================
2. ИЗ ЧЕГО СОБРАН (ТЕХНОЛОГИИ)
================================================================================
  - Язык: Python 3.11.2 (системный на сервере; venv /opt/aidev/venv)
  - Веб: FastAPI + uvicorn (лёгкий, ~50 МБ). Слушает 127.0.0.1:8090.
  - Интерфейс: чистый HTML/JS (без Node), страницы рендерит сам FastAPI.
  - База данных: SQLite (файл aidev.db), доступ через aiosqlite (асинхронно).
  - Нейросеть: Google Gemini через библиотеку google-genai:
      * основной канал — Vertex AI (корпоративный доступ Google Cloud);
      * резерв — AI Studio по API-ключу (если основной упал).
  - Проверки кода: ruff (линтер), mypy (типы), bandit (безопасность),
    pytest (тесты), ast.parse (синтаксис). Все — в песочнице.
  - git + gh (GitHub CLI) — зеркала репозиториев и создание Pull Request.
  - Настройки: файл .env читается библиотекой python-dotenv.
  - Алерты: httpx (async) шлёт сообщения в Telegram (Этап 2).
  - Запуск как служба ОС: systemd (служба aidev, авто-перезапуск).

Сервер: Debian 12, ~969 МБ RAM (узкое место), своп расширен. Служба aidev
ограничена MemoryMax=400M (чтобы не задушить рабочих ботов по памяти).

================================================================================
4. КАК ЗАПУСКАЕТСЯ И ЖИВЁТ НА СЕРВЕРЕ
================================================================================
Агент работает как системная служба systemd с именем aidev.
Юнит: scripts/aidev.service. Ключевое:
  User=aidev, Group=aidev              — отдельный служебный пользователь;
  WorkingDirectory=/opt/aidev
  EnvironmentFile=/opt/aidev/.env      — секреты подхватываются автоматически;
  ExecStart=.../uvicorn web.app:app --host 127.0.0.1 --port 8090;
  Restart=always, RestartSec=5         — упал -> ОС перезапустит;
  MemoryMax=400M, MemorySwapMax=0      — ЗАЩИТА рабочих ботов от OOM;
  логи -> journal (SyslogIdentifier=aidev).

Второй юнит aidev-sandbox-run.service — тестовый запуск кода (уровень L3,
порт 8091, заглушка до Этапа 2). Это ЕДИНСТВЕННАЯ служба, которую агенту
разрешено рестартовать.

ДОСТУП К ВЕБ-UI — только через SSH-туннель с машины владельца (Mac):
    ssh -N -L 8090:127.0.0.1:8090 shushpanchik_art@telegram-bot
(выполнять на МАКЕ, не на сервере). Затем открыть в браузере
http://127.0.0.1:8090. Наружу порт НЕ публикуется.

Команды управления службой (на сервере):
    systemctl restart aidev      — перезапустить
    systemctl status  aidev      — статус
    journalctl -u aidev -n50     — последние 50 строк лога

5. НАСТРОЙКИ (.env) — ЧТО КАЖДЫЙ ПАРАМЕТР ЗНАЧИТ
================================================================================
Файл .env (секреты). Все ключи также в .env.example. Читает config.py.
Хелперы _int/_float/_bool/_list безопасно превращают строки (пусто/мусор ->
берётся default).

  WEB_HOST                   — адрес прослушивания (127.0.0.1).
  WEB_PORT                   — порт веба (8090).
  WEB_AUTH_TOKEN             — секретный токен входа в UI (openssl rand -hex 24).

  GOOGLE_GENAI_USE_VERTEXAI  — "true" = использовать Vertex AI (основной канал).
  GOOGLE_CLOUD_PROJECT       — id проекта Google Cloud (из SMOKI).
  GOOGLE_CLOUD_LOCATION      — регион (us-central1).
  GEMINI_API_KEY_FALLBACK    — резервный ключ AI Studio (если Vertex упал).

  AI_TEXT_MODEL_FLASH        — модель Flash (gemini-2.5-flash) — ДЕШЁВАЯ, DEFAULT.
  AI_TEXT_MODEL_PRO          — модель Pro (gemini-2.5-pro) — умнее, дороже.
  AI_DEFAULT_MODEL           — модель по умолчанию: flash|pro.
  AI_FB_MODEL_FLASH          — имя Flash для резервного канала (gemini-flash-latest).
  AI_FB_MODEL_PRO            — имя Pro для резервного канала (gemini-pro-latest).
  AI_ESCALATION              — политика перехода на Pro: never|ask|auto (деф. ask).
  AI_DAILY_BUDGET_USD        — дневной лимит трат (3.0$); превышение блокирует Pro.
  AI_MAX_ITERATIONS          — сколько раз агент чинит красный gate (4).

  PRICE_FLASH_IN/OUT         — цена Flash за 1M токенов вход/выход (0.30 / 2.50).
  PRICE_PRO_IN/OUT           — цена Pro за 1M токенов вход/выход (1.25 / 10.0).
                               (Оценка стоимости каждого вызова -> таблица ai_usage.)

  SANDBOX_DIR                — где рабочие копии задач (/opt/aidev/sandbox).
  MIRRORS_DIR                — где зеркала репозиториев (/opt/aidev/mirrors).
  AUTONOMY_LEVEL             — уровень автономии по умолчанию 0|1|2|3 (деф. 1).
  MEM_MIN_AVAIL_MB           — порог свободной памяти (120 МБ); ниже — pytest
                               откладывается (шаг помечается пропущенным).

  ALLOWED_PROJECTS           — БЕЛЫЙ СПИСОК путей проектов (CSV). Только эти
                               проекты агент имеет право читать в песочнице
                               (/opt/SMOKI/bot,/opt/smoktolk/bot).

  TELEGRAM_BOT_TOKEN         — токен бота для алертов (Этап 2, опционально).
  TELEGRAM_CHAT_ID           — id получателя алертов (Этап 2, опционально).

  DB_PATH                    — путь к базе (/opt/aidev/aidev.db).
  LOG_LEVEL                  — уровень логов (INFO).

6. БАЗА ДАННЫХ — ВСЕ ТАБЛИЦЫ ПО ПОЛЯМ
================================================================================
Файл aidev.db (SQLite). Определение — db/schema.sql. Семь таблиц.

tasks — задачи владельца:
  id, project (путь проекта из allow-list), prompt (текст задачи),
  status (pending/running/done/error), autonomy_level (0-3),
  model_used (какая модель реально использовалась), branch (ветка PR),
  pr_url (ссылка на созданный Pull Request),
  review_approved (вердикт PRO: 1 одобрено / 0 с замечаниями / NULL нет),
  review_json (полный вердикт PRO как JSON), created_at, finished_at.

task_steps — шаги работы агента (живой лог):
  id, task_id, step_no (номер шага), kind (тип шага),
  input_summary, output_summary, gate_result, created_at.

ai_usage — журнал вызовов нейросети (учёт расхода):
  id, task_id, model, input_tokens, output_tokens,
  est_cost_usd (оценка стоимости), created_at.
  Функция today_cost_usd() суммирует траты за сегодня (для дневного бюджета).

diffs — сгенерированные правки (по файлам, мультифайл ложится штатно):
  id, task_id, file_path, diff_text (сам diff), applied (0/1), created_at.

gate_runs — результаты проверок gate:
  id, task_id, tool (ruff/mypy/...), exit_code, output_tail (хвост вывода),
  duration_sec, created_at.

attachments — вложения к задаче (файлы/скриншоты/буфер):
  id, task_id, kind (text/image), filename, mime,
  content_text (для текста), content_b64 (для картинок в base64), created_at.

settings — редактируемые настройки «ключ-значение»:
  key, value. Здесь хранятся переопределения из экрана «Настройки».

Индексы по task_id и created_at ускоряют выборки истории и стоимости.

================================================================================
7. УРОВНИ АВТОНОМИИ L0–L3
================================================================================
Определяют, насколько самостоятелен агент. Задаются на экране новой задачи
или переменной AUTONOMY_LEVEL (деф. 1).

  L0  read-only        — только советует, ничего не пишет.
  L1  sandbox-write    — ДЕФОЛТ: пишет в песочницу, гоняет gate, показывает
                         риски. Выход в прод — по кнопке владельца.
  L2  auto-PR          — при зелёном gate сам создаёт ветку и PR; мерж —
                         владелец. Здесь работает авто-выбор файлов.
  L3  auto-deploy-sbx  — катит в ТЕСТОВЫЙ инстанс aidev-sandbox-run (не прод).

Прод-мерж и рестарт прод-сервисов НЕ автоматизируются НИКОГДА.

================================================================================
8. КАК РЕШАЕТСЯ ЗАДАЧА: ПЛАН -> КОНТЕКСТ -> ПРАВКА -> GATE -> РЕВЬЮ -> PR
================================================================================
Файл agent/core.py. Две точки входа.

solve_task(task_id, task, rel_path, ...) — ОДНОФАЙЛОВЫЙ режим
(владелец указал конкретный файл). Шаги:
  1) Читается файл из песочницы (sandbox.read_file).
  2) generate_text(edit_prompt) — модель генерирует новую версию файла.
     extract_code() достаёт код из ответа (срезает markdown-обёртки ```).
  3) Файл записывается в песочницу (sandbox.write_file).
  4) run_gate(task_id) — прогон 6 проверок.
  5) ФИКС-ЦИКЛ: пока gate КРАСНЫЙ и есть итерации (< max_iterations):
       generate_text(fix_prompt) с выводом ошибок gate -> перезапись -> gate.
  6) collect_diff — итоговый diff всего каталога -> add_diff в БД.
  7) РЕВЬЮ (только если gate ЗЕЛЁНЫЙ): generate_text(review_prompt) моделью
     PRO -> parse_review -> вердикт «одобрено/с замечаниями» -> в БД.
  8) Возврат TaskOutcome (успех, число итераций, финальный gate, diff, review).

solve_task_auto(task_id, task, ...) — МУЛЬТИФАЙЛОВЫЙ режим (rel_path пуст,
агент сам решает какие файлы трогать). Шаги:
  1) explorer.project_tree — дерево файлов проекта.
  2) generate_text(explore_prompt) -> parse_files_list — модель ВЫБИРАЕТ
     файлы (до max_explore_files=8).
  3) explorer.read_many — читает выбранные файлы.
  4) generate_text(multifile_edit_prompt) -> parse_file_blocks — правки
     сразу по нескольким файлам (формат === FILE: path ===).
  5) Все файлы записываются в песочницу.
  6) run_gate -> фикс-цикл (multifile_fix_prompt), пока красно и есть итерации.
  7) collect_diff -> add_diff (по каждому файлу).
  8) РЕВЬЮ PRO (при зелёном gate) -> вердикт в БД.

Каждый шаг пишется в task_steps (живой лог виден в UI). Токены каждого
вызова -> ai_usage (учёт стоимости).

describe_screenshots() — отдельный шаг: если к задаче приложены картинки,
generate_multimodal описывает «что на скриншоте / что за ошибка», и это
подмешивается в контекст задачи.

================================================================================
9. ПЕСОЧНИЦА (SANDBOX): ИЗОЛЯЦИЯ КОДА ПРОЕКТА
================================================================================
Файл agent/sandbox.py. Три слоя изоляции — код проекта НИКОГДА не правится
напрямую, только копия.

  ШАГ 1. ЗЕРКАЛО (create_mirror). Проект из allow-list зеркалируется в
    MIRRORS_DIR/<project>.git через git clone --mirror (fetch-only, обратно
    не пушит). Уже существующее зеркало обновляется git remote update.

  ШАГ 2. РАБОЧАЯ КОПИЯ (prepare_workspace). Из зеркала делается
    git clone --local в SANDBOX_DIR/<task_id>/. Затем снимается snapshot-
    коммит («sandbox snapshot», --allow-empty) — чтобы потом diff показывал
    ТОЛЬКО правки агента, чисто.

  ШАГ 3. СНЯТИЕ СЕКРЕТОВ (_strip_secrets). Из копии УДАЛЯЮТСЯ:
    по именам — .env, venv, .venv, logs, __pycache__;
    по маскам — *.db, *.sqlite, *.sqlite3, *.log, .env.*
    То есть агент физически не видит секретов и боевой базы.

  ПРОВЕРКА ГРАНИЦ. _assert_allowed_project — проект обязан быть в
    ALLOWED_PROJECTS. _resolve_in_task / _assert_within_sandbox — любой путь
    файла резолвится и проверяется, что он ВНУТРИ каталога задачи (побег
    через ../ невозможен).

  ОПЕРАЦИИ: read_file, write_file, collect_diff (git diff всего каталога),
    cleanup (удаление рабочей копии).

  СОЗДАНИЕ PR (create_pull_request): ветка aidev/task-<id>, коммит правок,
    добавляется remote github (origin зеркала), push --force в эту ветку,
    затем gh pr create --repo owner/repo --head branch. Возвращает URL PR.
    owner/repo вычисляется из origin-URL (_github_repo).

================================================================================
10. EXECUTOR: ALLOW-LIST КОМАНД (СЕРДЦЕ БЕЗОПАСНОСТИ)
================================================================================
Файл agent/executor.py. ЕДИНСТВЕННАЯ точка запуска внешних команд. Принцип —
БЕЛЫЙ список (allow-list), а не чёрный. Всё, чего нет в списке, — отказ.

  ALLOWED_COMMANDS: словарь «имя команды -> абсолютный путь к бинарю».
    В списке только инструменты проверки: python, ruff, mypy, bandit, pytest
    (конкретные пути из venv). Никаких bash, rm, curl, git, sudo — их НЕТ.

  Функция run(argv, workdir, timeout):
    - argv[0] — имя из ALLOWED_COMMANDS (НЕ абсолютный путь). Нет в списке ->
      ExecutorError, запуск НЕ производится.
    - workdir обязан быть ВНУТРИ песочницы (is_within_sandbox), иначе отказ.
    - перед тяжёлым запуском проверяется свободная память
      (available_memory_mb); ниже MEM_MIN_AVAIL_MB -> ExecutorError «отложено».
    - subprocess.run с shell=False ВСЕГДА, минимальным окружением
      (_minimal_env, без утечки лишних переменных), с таймаутом.
    - таймаут -> ExecutorError; любая ошибка запуска -> ExecutorError.

  Таким образом агент физически не может выполнить rm/curl/выйти из песочницы/
  sudo на прод — это самый важный барьер (тест test_executor — ключевой).

11. GATE: БАРЬЕР ИЗ 6 ПРОВЕРОК ПЕРЕД PR
================================================================================
Файл agent/gate.py. Перед тем как правка будет предложена владельцу, она
проходит барьер. Красный gate -> правка НЕ показывается, агент чинит сам.

  Шесть шагов (по порядку):
    1) ast.parse каждого .py — синтаксис (без subprocess, прямо в питоне).
       Если синтаксис сломан — остальные шаги ПРОПУСКАЮТСЯ (нет смысла).
    2) ruff check .   — линтер стиля и потенциальных ошибок.
    3) mypy .         — проверка типов.
    4) bandit -ll -r .— сканер безопасности (только средние/высокие).
    5) pytest -q      — весь набор тестов задачи.
    6) smoke          — импорт затронутых модулей (python -c "import ...").

  GateResult.passed — True, если все НЕ пропущенные шаги зелёные.
  summary() — однострочная сводка вида «ruff ✅ mypy ✅ pytest ❌».
  red_tools() — список красных инструментов (идёт модели в фикс-цикл).

  ПАМЯТЬ: если перед pytest мало памяти — шаг помечается skipped (пропущен),
  а НЕ красным (чтобы нехватка RAM не блокировала работу; предупреждение в UI).

  Результаты каждого шага пишутся в gate_runs (log_gate_to_db).

12. ОБЩЕНИЕ С НЕЙРОСЕТЬЮ GOOGLE (VERTEX AI + РЕЗЕРВ, FLASH/PRO)
================================================================================
Файл ai/gemini.py.

  ДВА КЛИЕНТА:
    - основной (get_client): genai.Client() c Vertex AI — доступ из окружения
      (GOOGLE_GENAI_USE_VERTEXAI, GOOGLE_CLOUD_PROJECT, GOOGLE_CLOUD_LOCATION,
      service account / ADC).
    - резервный (get_fallback_client): genai.Client(api_key=...) с ключом
      GEMINI_API_KEY_FALLBACK (AI Studio). Нет ключа -> резерва нет.

  АВТОПЕРЕКЛЮЧЕНИЕ: _clients() возвращает [primary, fallback]. Вызов идёт по
  очереди: если primary упал (лимит/сбой), пробуется fallback, в лог пишется
  «использован резервный ключ». На резервном канале имя модели подменяется
  (fb_model_name: gemini-flash-latest / gemini-pro-latest).

  ВЫБОР МОДЕЛИ НА ЛЕТУ: аргумент model = 'flash' | 'pro' | полное имя.
  _resolve_model превращает flash/pro в реальное имя из config.

  generate_text(prompt, model, temperature, max_output_tokens):
    Генерация текста. Возвращает GenResult (text, input_tokens, output_tokens,
    model, via=primary|fallback). Есть повторные попытки при временных сбоях
    (_call_with_retry / _is_transient).

  generate_multimodal(prompt, images, model, ...):
    Текст + картинки (vision). images — список (данные_байты, mime_type).
    Картинки заворачиваются в types.Part.from_bytes. Тот же путь
    primary -> fallback и учёт токенов. Для скриншотов ошибок «реши проблему».

  МОДЕЛИ И СТОИМОСТЬ (факт):
    Flash gemini-2.5-flash — $0.30 вход / $2.50 выход за 1M токенов. ДЕФОЛТ.
    Pro   gemini-2.5-pro   — $1.25 / $10 (дороже, умнее). Для ревью/сложного.
    Реальный бюджет ~$1–5/мес на Flash. Дневной лимит AI_DAILY_BUDGET_USD.

  ГИБРИДНЫЙ РЕЖИМ: по умолчанию Flash. Если задача сложная или Flash не
  осилил gate — по политике AI_ESCALATION (never|ask|auto) агент либо
  спрашивает владельца в UI «переключить на Pro? оценка $0.X», либо
  переключается сам (auto), либо не трогает (never). Превышение дневного
  бюджета блокирует Pro.

14. ВЕБ-ИНТЕРФЕЙС: ЭКРАНЫ И КНОПКИ
================================================================================
Файл web/app.py. Владелец — не программист, код читает на GitHub в PR.
UI даёт РЕШЕНИЕ на человеческом языке. Все страницы рендерит сам FastAPI
(_page — общий каркас).

  АУТЕНТИФИКАЦИЯ (require_auth): токен из заголовка Authorization: Bearer
  <WEB_AUTH_TOKEN> ИЛИ из cookie auth (для браузера). Без токена — 401.
  Служебные /healthz и /login — без auth.

  /login  — форма ввода токена. При верном токене ставится cookie auth
            (httponly, samesite=strict, на сутки) и редирект на главную.

  /  (Новая задача) — форма: текст задачи + выбор проекта (из allow-list) +
     уровень L0–L3 + (опционально) путь конкретного файла + загрузка файлов
     (UploadFile) и вставка текста из буфера (textarea). Кнопка «Запустить».
     Если путь файла пуст -> solve_task_auto (агент сам выберет файлы),
     иначе -> solve_task (правит указанный файл).

  /history — список задач: статус, проект, модель, ссылка на PR.

  /task/{id} — страница задачи. Показывает:
     живой лог шагов агента (task_steps) с ✓/✗;
     блок РЕВЬЮ PRO (review_json): вердикт «одобрено / с замечаниями»;
     diff-сводку; кнопку «Создать PR» (POST /api/task/{id}/pr).
     Замысел SPEC: три блока — «Что сделано» / «Риски» / «Проверки».

  /settings — модель по умолчанию, политика эскалации, дневной бюджет.

  ЗАПУСК ЗАДАЧИ (POST /api/task): создаётся запись в tasks, сохраняются
  вложения (_store_attachments -> add_attachment), затем solve_task или
  solve_task_auto запускается в ФОНОВОМ потоке (run_in_executor), т.к. он
  синхронный и CPU/IO-bound; UI не блокируется, шаги пишутся в БД по ходу.

  СОЗДАНИЕ PR (POST /api/task/{id}/pr): sandbox.create_pull_request ->
  ветка, push, gh pr create -> URL сохраняется в tasks.pr_url.

16. ОРКЕСТРАТОР: FLASH-ИСПОЛНИТЕЛЬ -> PRO-РЕВЬЮЕР
================================================================================
Идея: дешёвая быстрая модель (Flash) исполняет задачу, умная (Pro) — РЕВЬЮИТ
результат ВМЕСТО владельца. Реализовано в core.py в обеих ветках решения.

  После ЗЕЛЁНОГО gate: generate_text(review_prompt(task, diff, gate_summary))

  и показывается на /task/{id}. Владелец видит мнение старшей модели и решает,
  мержить ли PR. В прод — только ручной мерж.

20. БЕЗОПАСНОСТЬ И КОНТРОЛЬ КАЧЕСТВА (CI)
================================================================================
Свой приватный репозиторий aidev-assistant. Ветка main ЗАЩИЩЕНА: прямых
коммитов нет. Любое изменение — через отдельную ветку и Pull Request, который
проверяется автоматикой (CI) и сливается только после «зелёного» отчёта.

CI-джобы (наследуют культуру ботов): syntax, ruff, bandit -ll, pytest+cov
(fail < 45%), mypy, gitleaks; далее pip-audit, codespell, yamllint,
markdownlint. Версии ruff/mypy в venv = как в CI. Перед push локально:
    venv/bin/ruff check <файлы> && venv/bin/python -m mypy <файлы>

НЕИЗМЕННЫЕ ПРИНЦИПЫ БЕЗОПАСНОСТИ:
  - Агент НИКОГДА не получает bash/rm/curl — только executor allow-list.
  - Всё в песочнице sandbox/<task>/ без .env/БД/логов.
  - Ручной мерж PR владельцем — единственный путь в прод.
  - Прод-сервисы ботов агент не рестартует; только aidev-sandbox-run.

Git flow: ветка feature|fix|chore|docs -> add/commit/push -> gh pr create ->
CI зелёный -> merge в UI -> main pull -> branch -d.
